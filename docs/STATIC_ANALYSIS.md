# Статический анализ OpenAPI и FastAPI

Модуль пункта 1 сравнивает файл OpenAPI с исходным Python-кодом FastAPI.
Исходники читаются через AST: они не импортируются и не исполняются.
Работающий микросервис и LLM для проверки не нужны.

## Что изменилось

1. Распознаются `def`, `async def`, строковый `path=`, `api_route` с несколькими
   HTTP-методами, несколько декораторов и префиксы подключённых роутеров.
   Исправлен абсолютный импорт роутеров. Неподключённый роутер при наличии
   приложения не выдаётся за зарегистрированный маршрут.
2. Поддержаны `Annotated`, `str | None`, `Optional`, строковые аннотации,
   простые `Literal` со строками, числами и bool. Обязательность определяется
   отдельно от nullable, с учётом `Field`, `default` и `default_factory`.
   Семантика обязательности моделей ориентирована на Pydantic 2.
3. Учитываются `alias` параметров и полей, `Header(convert_underscores=False)`,
   `Body(embed=True)`. Имена HTTP-заголовков сравниваются без учёта регистра.
   Сравнивается обязательность параметров и тела запроса.
4. Статус обычного POST без явного `status_code` теперь 200, а не ошибочно
   предполагаемый 201. Явный числовой статус сохраняется.
5. Неизвестный тип, неизвестная или рекурсивная модель, неоднозначная схема,
   неподдерживаемая конфигурация ответа дают `analysis_limitation` для ревью,
   вместо утверждения о доказанном расхождении.
6. Исправлено объединение простых объектных `allOf`; конфликтующие варианты,
   сложные объединения и отсутствующие ссылки не подменяются достоверной схемой.
   Поддержаны распространённые записи nullable в OpenAPI 3.0 и 3.1.
7. Можно передать каталог исходников или один Python-файл. При обходе исключаются
   `.venv`, `venv`, `.git`, `__pycache__`, `site-packages` и `node_modules`.

## Пример на понятных данных

В `checks/static_analysis/examples` лежит небольшой искусственный пример:

| Ситуация | Результат |
|---|---|
| В спецификации `search` обязателен, в коде есть значение по умолчанию | `required_drift` |
| Спецификация требует строку `nickname`, код допускает `None` | `nullability_drift` |
| Модель `ExternalUser` отсутствует в исходниках | `analysis_limitation`, нужен ручной разбор |

Внешняя модель намеренно отсутствует. Это пример входного текста для статического
анализатора, а не готовый сервер для запуска.

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
.\.venv\Scripts\python.exe -m drift_agent.cli --spec checks/static_analysis/examples/openapi.yaml --src checks/static_analysis/examples/app.py --output-format json --output-file .venv/static-demo.json
```

## Формат находки версии 1.1

Старые поля и значения девяти категорий сохранены. Добавлены поля, позволяющие
другим модулям определить происхождение находки и необходимость ревью.
Формальная схема одного элемента `items` находится в `static-findings.schema.json`.

| Поле | Смысл |
|---|---|
| `id` | Детерминированный идентификатор; одинаковый повторный анализ даёт те же ID |
| `endpoint` | Метод и адрес; `*` для общей диагностики исходников |
| `category` | Существующая drift-категория либо `analysis_limitation` |
| `location` | Логический путь к параметру/полю; это не JSON Pointer для применения патча |
| `detail` | Объяснение расхождения или ограничения анализа |
| `spec_evidence`, `code_evidence` | Значения со стороны спецификации/кода либо `null` |
| `severity` | `error`, `warning`, `info`; существующие правила приоритетов не заменены |
| `schema_version` | `1.1` |
| `source_kind` | `static` |
| `source_file`, `source_line` | Файл относительно корня анализа и строка обработчика; `null`, если неизвестны |
| `requires_review` | `true`, когда результат нельзя считать подтверждённым расхождением |

`analysis_limitation` — диагностическая категория, не доказательство ошибки API.
У неё `severity=info` и `requires_review=true`. Существующий счётчик `summary.total`
включает эти элементы; для числа подтверждённых расхождений нужно исключить их.
LLM-слой возвращает для них `AMBIGUOUS`, без запроса объяснения и без предложения патча.
При включении режима explain существующая инициализация провайдера всё ещё выполняется.

Потребителям JSON следует разрешать новые поля и учитывать новую категорию.
Строгие внешние enum-проверки нужно обновить. Это выходной контракт статического
модуля; объединение с динамическим анализатором и настройка приоритетов остаются
пунктом 3. Итоговый экспорт после ревью из пункта 6 не изменялся.

## Неопределённость и ограничения

Вычисляемые адреса/методы, программная регистрация через `add_api_route`/`mount`,
неразрешённые подключения и циклы роутеров отражаются в диагностике исходников.
При такой диагностике отсутствие маршрута и неизвестный итоговый путь не объявляются
доказанным расхождением. Это консервативное поведение может уменьшать число находок.
`NormalizedContract.metadata.analysis_complete` в этом этапе относится к обнаруженным
ограничениям регистрации маршрутов; полноту схем и параметров нужно оценивать по
`analysis_notes`, `analysis_note` и выходным `analysis_limitation`.

Зависимости `Depends`/`Security`, модели query-параметров, несколько параметров тела,
Form/File, дополнительные ответы, вычисляемые статусы и пользовательские классы
ответа полностью не разворачиваются; соответствующая часть сравнения требует ревью.
Обычный возвращаемый словарь без модели ответа не считается полным контрактом.
Рекурсивные схемы разворачиваются до первого повтора. Сложные объединения типов,
раздельные validation/serialization aliases также требуют ревью.

Поддержка OpenAPI — статическое подмножество 3.0/3.1, не полная реализация JSON Schema.
Внешние `$ref` не загружаются; существующий parser сообщает о неподдерживаемой ссылке.
Валидаторы Pydantic, произвольные фабрики приложений и динамический Python могут
требовать ручного разбора. Анализатор не доказывает фактическое поведение сервиса.
